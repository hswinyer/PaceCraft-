    Step 3 of 4 — Strategy Hub

    How This System Works

    This is the end page. It explains the target user, the value model, every requirement, the data flow diagrams, and the end-to-end process model.

    The target user

    Primary user group: Amateur long-distance runners who are training for a timed road race between 5K and marathon distance and need to calculate, validate, and store realistic mile-by-mile pacing splits so they do not burn out early and miss their goal time. These runners own a watch and a race entry, but they have no coaching background, so they guess at pace and discover their mistake at mile twenty. They need a plan they can trust, written in minutes per mile, saved somewhere they can find it again on race morning.

    Secondary stakeholder: The running club coach or pacing coordinator, who oversees the system, audits submitted race strategies for cardiovascular safety, and approves or flags pacing plans before race day.

    The value model

    Funded by a sponsor (Garmin). Runners get advanced pacing analytics and watch-ready split schedules for free, and coaches get a shared safety review tool at no cost. Garmin bears one hundred percent of development, hosting, and maintenance cost, and keeps the system running because it drives wearable hardware sales, brand loyalty, and continued use of the Garmin Connect ecosystem.

    Requirements

    Functional requirements

    FR-01The system shall allow a runner to create and save a race pacing plan by entering runner name, race distance, goal finish time, and strategy type.
    FR-02The system shall calculate the average pace per mile and generate a mile-by-mile target split schedule from the distance, goal time, and strategy type.
    FR-03The system shall block plan submission and display an error message citing BR-01 when the calculated average pace is faster than four minutes thirty seconds per mile.
    FR-04The system shall filter saved pacing plans in real time by runner name, race distance, or review status.
    FR-05The system shall allow a user in the running coach role to change a plan status from Draft to Coach Approved or Flagged (High Risk), and shall record that decision in a review log.
    FR-06The system shall display a summary report showing total saved plans, coach-approved plans, flagged plans, and the average target pace across all records.
    FR-07The system shall issue a unique Access ID on first arrival, store it in the browser, and restore a returning user's saved plans when that ID is entered again.

    Non-functional requirements

    NFR-01Performance. The system shall filter and re-render strategy search results within five hundred milliseconds of a keystroke.
    NFR-02Reliability. The system shall retain one hundred percent of created and updated pacing plans across browser refreshes using browser storage.
    NFR-03Usability. The system shall update the visible role capabilities and disable restricted coach buttons immediately when the role selector changes, with no page reload.

    Business rules

    BR-01Safety pace floor. No amateur pacing plan may target an average pace faster than four minutes thirty seconds per mile.
    BR-02Marathon fatigue rule. Any marathon plan using a positive split strategy is automatically marked Flagged (High Risk) when it is created.
    BR-03Approval authority. Runners may not approve their own pacing plans. Only a user acting in the running coach role may set a plan status to Coach Approved.

    Constraints

    CON-01The system must run entirely inside the browser using local browser storage, with no database server, no real authentication, and no paid services.
    CON-02All generated split schedules must use standard mile-based pacing metrics so they stay compatible with Garmin wearable workout imports.

    Data stores used by the system

    D1 pacecraft_plansPlan ID, owner Access ID, runner name, distance, goal seconds, strategy, average pace seconds, split schedule, status, created date.
    D2 pacecraft_usersAccess ID, display name, date first issued, date last seen.
    D3 pacecraft_reviewsReview ID, plan ID, runner name, decision, reviewer role, decision date.

    Store names match the browser storage keys used in the code exactly.

    Business process model: create and approve a race strategy

    One end-to-end process, with one exclusive decision and one exception path. Each task is marked manual or system-supported, and every system-supported task names the data flow diagram process it maps to.

    flowchart TB
  START((Start: runner decides to race)) --> T1
  T1["Manual: choose a goal finish time and race distance"] --> T2
  T2["System-supported: issue or restore access identifier (DFD 1.0)"] --> T3
  T3["Manual: enter name, distance, goal time, and strategy"] --> T4
  T4["System-supported: calculate average pace and mile splits (DFD 2.0)"] --> T5
  T5["System-supported: apply safety pace floor and fatigue rule (DFD 3.1 to 3.3)"] --> D1

  D1{"Exclusive decision: is the average pace safe under BR-01?"}
  D1 -- "No: pace faster than 4:30 per mile" --> EX1
  D1 -- "Yes" --> T6

  EX1["Exception path. System-supported: block the save and display the BR-01 safety message (DFD 3.2)"] --> EX2
  EX2["Manual: runner raises the goal finish time"] --> T3

  T6["System-supported: save the plan as Draft or Flagged (DFD 3.4)"] --> T7
  T7["Manual: coach opens the strategy hub before race day"] --> T8
  T8["System-supported: check reviewer role under BR-03 (DFD 4.2)"] --> D2

  D2{"Is the reviewer acting as a running coach?"}
  D2 -- "No" --> EX3
  D2 -- "Yes" --> T9
  EX3["System-supported: refuse the approval and show the BR-03 message, plan stays Draft (DFD 4.2)"] --> ENDB

  T9["System-supported: set status to Coach Approved or Flagged and write the review log (DFD 4.3 and 4.4)"] --> T10
  T10["System-supported: show the summary report and export the watch ready splits (DFD 6.0 and 3.5)"] --> T11
  T11["Manual: runner saves the access identifier and runs the race to plan"] --> ENDA

  ENDA((End: approved plan on race day))
  ENDB((End: plan returned to the runner as unapproved draft))

    Drawn with Mermaid. The exception path ends either back at data entry or at a meaningful unapproved-draft end event.
